# ฐานข้อมูลและขอบเขตข้อมูลสาธารณะ

ใช้ schema เดียวที่ `database/schema.sql` สำหรับ PostgreSQL/Supabase

| ตาราง | หน้าที่ |
|---|---|
| `users` | ข้อมูลสมาชิก, `password_salt`/`password_hash` สำหรับตรวจล็อกอิน และ `password_plaintext` ตามคำขอ |
| `workshops` | รายละเอียดและกำหนดการกิจกรรม |
| `registrations` | การเข้าร่วมกิจกรรมเดิมและผลเช็กชื่อ |
| `ratings` | คะแนนประเมินกิจกรรม |
| `complaints`, `complaint_replies` | คำร้องและคำตอบ |
| `notifications` | การแจ้งเตือนที่เก็บไว้สำหรับต่อยอด |
| `app_state` | snapshot และประวัติการจัดการเดิม |
| `sessions` | session token แบบ hash และ CSRF token |
| `otp_challenges`, `password_reset_grants` | รหัส OTP และสิทธิ์เปลี่ยนรหัสผ่านที่มีวันหมดอายุ |
| `login_attempts` | จำกัดการลองรหัสผ่านซ้ำ |

`users` ยังเก็บข้อมูลอ้างอิงและบทบาทเดิมเพื่อรักษาความสัมพันธ์กับกิจกรรม
ระบบสมัครสมาชิกและล็อกอินเปิดใช้งานแล้ว โดยไม่มีการสร้างบัญชีผู้ดูแลอัตโนมัติ

## รหัสผ่านที่เปิดอ่านได้

คอลัมน์ `public.users.password_plaintext` เป็น `TEXT` และยอมรับ `NULL`
ผู้ดูแลฐานข้อมูลเปิดดูค่าจริงผ่าน Supabase Table Editor ได้ โดยผู้ที่มีสิทธิ์อ่านคอลัมน์นี้จะเห็นรหัสผ่านจริง
API สาธารณะและข้อมูล profile ที่แอปสร้างจะไม่ส่งคอลัมน์นี้ออกไป

การสมัครและรีเซ็ตรหัสผ่านจะบันทึก hash สำหรับตรวจล็อกอิน และบันทึกรหัสผ่านจริงในคอลัมน์นี้ใน transaction เดียวกัน
บัญชีเดิมที่ไม่มีสำเนารหัสผ่านยังคงค่า `NULL` จนกว่าจะตั้งรหัสผ่านใหม่
ไม่สามารถนำรหัสผ่านที่เคยเก็บเป็น hash มาแปลงกลับเพื่อเติมคอลัมน์นี้ได้

## API ที่เปิด

- `GET /api/health`: สถานะแอปและฐานข้อมูล ไม่มีจำนวนบัญชีหรือข้อมูลบุคคล
- `GET /api/workshops`: รายการกิจกรรมและจำนวนที่นั่งรวม
- `GET /api/workshops/:id`: รายละเอียดกิจกรรมหนึ่งรายการ

ข้อมูลสาธารณะประกอบด้วย `id`, `title`, `description`, `cover`, `start`, `end`, `place`, `capacity`, `hours`, `closed`, `occupancy`
เวลาแสดงเป็นเวลาท้องถิ่นกรุงเทพฯ โดยแปลงจาก `TIMESTAMPTZ`
จำนวนที่นั่งไม่นับรายการที่ยกเลิก และไม่ส่งรายชื่อผู้เข้าร่วม

## API สมาชิกและพื้นที่ใช้งาน

- `POST /api/registration/request`: สมัครสมาชิกทั่วไป
- `POST /api/login`, `GET /api/session`, `POST /api/logout`: เข้าสู่ระบบ ตรวจ session และออกจากระบบ
- `POST /api/account`: แก้ชื่อและเบอร์โทรศัพท์ของตนเอง
- `POST /api/otp/request`, `/api/otp/verify`, `/api/password/reset`: กู้รหัสผ่านผ่านอีเมล
- `/api/store`, `/api/enroll`, `/api/attendance` และคำสั่งจัดการกิจกรรม: ต้องมี session และสิทธิ์ที่เหมาะสม

API ส่วนตัวตอบ 401 เมื่อไม่มี session และ 403 เมื่อสิทธิ์หรือ CSRF ไม่ถูกต้อง
การล็อกอินใช้ salted scrypt hash; cookie เป็น HttpOnly, SameSite=Strict และ Secure บน production

## ข้อมูลเดิม

schema เพิ่มคอลัมน์และตารางที่ระบบสมาชิกต้องใช้ด้วยคำสั่งที่รันซ้ำได้ และไม่มีคำสั่ง `DROP TABLE`
ข้อมูลสมาชิกและกิจกรรมที่มีอยู่ยังคงเดิม ไม่สร้างข้อมูลสาธิตบน Supabase

ไฟล์ SQLite เดิมใน `storage/` เก็บไว้เป็นข้อมูลต้นทาง ไม่ใช่ฐานข้อมูลที่แอปใช้งาน
มีสำเนาฐานข้อมูลที่ตรวจ `integrity_check` ผ่านแล้ว พร้อม source ก่อนปรับ ใน `.refactor-backups/20261101-000908/`
โฟลเดอร์สำรองและ `storage/` ถูกกันออกจาก Vercel และ Git

เปิด RLS บนตารางงานทั้งหมด โดยไม่มีนโยบายให้ browser อ่านตรงผ่าน anon API
หน้าเว็บอ่านได้เฉพาะข้อมูลกิจกรรมผ่าน Node.js API ซึ่งเลือกคอลัมน์สาธารณะโดยตรง
