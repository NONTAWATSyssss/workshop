# ผลตรวจโค้ดและทดสอบระบบ — 1 พฤศจิกายน 2569

ตรวจเส้นทาง Frontend, API, สมาชิกและสิทธิ์, การบันทึกข้อมูล, คำร้อง, การโหลดไฟล์ และการทำงานเบื้องหลังของ User/Staff โดยรักษา UI และฟอนต์เดิม

## ผลตรวจสุดท้าย

- `npm test`: ผ่าน **94/94** รายการ จากเดิม 88 รายการ
- `npm run check`: ตรวจ syntax ผ่าน 45 ไฟล์ JavaScript
- `npm run format:check`: ผ่านทุกไฟล์ที่กำหนด
- Chrome: ผ่าน **19 ขั้นตอน** กับแอปและฐานข้อมูล PostgreSQL จำลองจริง ไม่พบ uncaught JavaScript error หรือ API error ในรอบที่ทดสอบสำเร็จ
- `npm audit --omit=dev`: ไม่พบช่องโหว่ใน dependencies ที่ใช้งานจริง ณ เวลาตรวจ ไม่ได้เปลี่ยนเวอร์ชันแพ็กเกจ
- `git diff --check`: ผ่าน
- การสมัครสมาชิก เขียนข้อมูล และลบข้อมูลระหว่างทดสอบ ใช้ฐานข้อมูล PGlite แยกจาก Supabase ของโครงการ

## จุดหน่วงที่พบและแก้แล้ว

| งาน | ก่อนแก้ | หลังแก้ |
| --- | --- | --- |
| แก้ชื่อกิจกรรม 1 รายการ ในชุดจำลอง 41 เวิร์กช็อป / 30 คำร้อง / 60 คำตอบ | 185 คำสั่ง SQL; ประมาณ 2.9 วินาที | 10 คำสั่ง SQL; ประมาณ 0.17–0.21 วินาที |
| สร้าง snapshot ในชุดจำลองเดียวกัน | 99 คำสั่ง SQL | 10 คำสั่ง SQL |

เวลาในสองแถวแรกเป็น benchmark แยกจากฐานข้อมูลจริง โดยจำลองความหน่วง 10 ms ต่อคำสั่ง SQL และใช้ข้อมูลชุดเดิมก่อน/หลัง ตัวเลขนี้ไม่ใช่เวลารับประกันบน Supabase หรือ Vercel ผลที่ยืนยันได้โดยตรงคือจำนวนคำสั่ง SQL และพฤติกรรมที่ทดสอบผ่าน

การอ่าน `/api/workshops` ผ่าน Node server ของโครงการจริงระหว่างตรวจ ได้ HTTP 200 ทั้ง 3 ครั้ง ขนาด JSON 12,990 ไบต์ เวลา 511, 202 และ 201 ms เส้นทางนี้ใช้ SQL 1 คำสั่ง จึงยังมีเวลารอเครือข่ายฐานข้อมูลที่แยกจากการประมวลผลภายในเว็บ

## การแก้ไขตามไฟล์

| ไฟล์ | สิ่งที่แก้ |
| --- | --- |
| `src/features/workshops/store.js` | อ่านคำตอบคำร้องด้วย JOIN ครั้งเดียว; รวมคำตอบด้วย Map; บันทึกเฉพาะแถวที่เปลี่ยน; ไม่เขียนคำตอบเก่าซ้ำ; นับผู้เข้าร่วมด้วยการวนรายการครั้งเดียว; ตัดเงื่อนไขอ่านข้อมูลเฉพาะสมาชิกที่ไม่เคยถูกเรียกในตัวสร้าง snapshot; ไม่อ่านฟิลด์รหัสผ่านในชุดโปรไฟล์สำหรับ snapshot |
| `src/features/workshops/management.js` | ใช้ snapshot ก่อนแก้ที่ตรวจสอบแล้วร่วมกับตัวบันทึก; ตัดการอ่าน revision ซ้ำ; แก้ `/api/enroll` ที่อ้าง `workshopRows` โดยไม่ได้รับเข้ามา และอ่านผลลัพธ์ก่อน COMMIT เพื่อไม่ตอบ Error หลังบันทึกสำเร็จ |
| `public/assets/js/app.js` | ป้องกัน polling ซ้อน; ไม่ poll ในแท็บที่ซ่อน; ไม่ใช้ผลลัพธ์เก่าระหว่างบันทึกหรือพิมพ์; ตรวจรุ่นเซสชันเพื่อไม่ให้ผลตอบกลับจากเซสชันเก่าทำให้บัญชีที่เพิ่ง Login หลุด |
| `src/core/http.js` | เพิ่ม ETag และ Last-Modified สำหรับไฟล์ static; รองรับ conditional GET/HEAD; ตรวจความเปลี่ยนแปลงก่อนใช้ไฟล์เดิม; API ข้อมูลส่วนตัวยังคงนโยบาย cache เดิม |
| `tests/performance.test.js` | เพิ่มชุดข้อมูลทดสอบขนาดใหญ่; กำหนดจำนวนคำสั่งสูงสุด; ตรวจว่าไม่เขียนแถวเดิมซ้ำ; ตรวจการลดที่นั่งและ API ลงทะเบียนโดยตรง |
| `tests/public-ui.test.js` | เพิ่มการทดสอบ polling ช้า/ซ้อน, แท็บที่ซ่อน, การพิมพ์ระหว่างรอข้อมูล และผลตอบกลับของเซสชันเก่า |
| `tests/http.test.js` | ตรวจ ETag, GET/HEAD แบบ 304, การแก้เนื้อหาไฟล์แล้วได้ไฟล์ใหม่ และไฟล์ที่ไม่มีอยู่ |
| `scripts/profile-workspace.js` | เพิ่ม benchmark สำหรับการสร้าง snapshot และแก้กิจกรรมเมื่อมีข้อมูลอื่นจำนวนมาก; ใช้เฉพาะฐานข้อมูลจำลอง |
| `package.json` | เพิ่มคำสั่ง `npm run profile:workspace` สำหรับวัดซ้ำ |

ไม่มีการลบรูปภาพ migration หรือ endpoint ที่ยังเป็นส่วนหนึ่งของ API เพียงเพราะไม่พบการเรียกจากหน้าเว็บปัจจุบัน

การทดสอบอัตโนมัติเพิ่มเติมครอบคลุมรหัสผ่านผิด การจำกัดการลอง Login, CSRF, การเปลี่ยนสิทธิ์จากฐานข้อมูล, รูปโปรไฟล์และการเข้าถึงรูป, OTP ด้วยตัวส่งอีเมลจำลอง, ฟอร์ม/ปฏิทิน/เวลา, ชั่วโมงอบรมและการยืนยันผล, การลบกิจกรรม, การเก็บคำร้อง 15 วัน, และการแยกข้อมูลผู้ใช้

ทดสอบความสามารถในการจับ regression โดยปิดตัวกัน polling ซ้อนเฉพาะใน VM ทดสอบ พบว่าเทสต์ล้มตามที่คาด และเมื่อใช้โค้ดจริงเทสต์ผ่าน โดยไม่ได้แก้ไฟล์เว็บที่ให้บริการระหว่างทดลองนี้

## ประเด็นที่ต้องทราบก่อนใช้งานจริง

- **รหัสผ่านแบบอ่านได้:** ฐานข้อมูลยังเก็บรหัสผ่านในรูปแบบอ่านได้ตามคำขอเดิม ผู้ที่เข้าถึงคอลัมน์นั้นอ่านรหัสผ่านสมาชิกได้ แนะนำให้เก็บเฉพาะ hash ก่อนเปิดใช้งานจริง การตรวจรอบนี้ไม่ได้เปลี่ยนนโยบายดังกล่าว และเทสต์ยังตรวจว่า API ไม่ส่งค่ารหัสผ่านออกมา
- **การเติบโตของข้อมูล:** ระบบยังใช้ snapshot รวมและล็อกการเขียนร่วมกันเพื่อรักษาความถูกต้อง เมื่อมีข้อมูลหรือผู้ใช้พร้อมกันจำนวนมาก ควรวัดโหลดของ deployment จริงก่อนพิจารณาแยก API/แบ่งหน้าที่ฝั่งเซิร์ฟเวอร์ การทดสอบรอบนี้ไม่ได้เป็น load test ของ Supabase จริง
- **บริการภายนอก:** ไม่ได้ส่งอีเมล SMTP จริงหรือ deploy ไป Vercel ในรอบนี้ ผลของ SMTP, CDN, เครือข่าย และ cold start บน deployment จริงจึงต้องตรวจในสภาพแวดล้อมที่จะเปิดใช้ การ cache ไฟล์ static บน Vercel เป็นหน้าที่ของแพลตฟอร์ม ส่วนเทสต์ 304 ในรายงานตรวจ Node server ของโครงการ
